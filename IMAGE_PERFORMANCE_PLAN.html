1Resize and re-encode the source images

This is the whole ballgame. 85% of your image weight is pure waste — pixels nobody ever sees. Vite copies whatever you import straight into dist/ untouched, so the browser downloads the camera-original file.

Two problems compound. The images are far larger than they're displayed (a 30-megapixel photo in a 200px avatar), and they're in PNG/JPEG when WebP does the same job in a fraction of the bytes. WebP is supported by every browser that matters now and costs nothing to use.

The script is already written and in your repo

scripts/optimize-images.mjs walks src/assets, resizes each image to the width it's actually rendered at, re-encodes to WebP, and rewrites the import statements to point at the new files. It never upscales, and it skips any file that would get bigger. 

# see what it would do — writes nothing
node scripts/optimize-images.mjs

# apply it: adds .webp files, repoints imports
node scripts/optimize-images.mjs --write
npm run build

# undo everything if you don't like it
git checkout -- src

Originals are left on disk, so nothing is destroyed and git is your safety net. Review the diff before committing.

Why this is the highest-value change

41.5 MB removed from a marketing site is the difference between a first visit that feels instant and one that doesn't — especially on mobile data, which is most of your African audience. It also directly reduces your Vercel bandwidth usage, which matters because the Hobby plan caps at 100 GB/month.

2Stop lazy-loading the images above the fold

There's a real bug here, and it's the opposite of the usual advice. src/components/figma/ImageSlot.tsx hardcodes loading="lazy" on every image it renders (line 98): 

<img
  src={src}
  alt={label}
  loading="lazy"          // ← applied to the nav logo too
  className={...}
/>

But FigmaNav renders the logo through that same component (slot="nav-logo"), and the /cococycle-hub hero background goes through it too. So your header logo and that hero are being deliberately deferred — the browser holds them back until layout settles. That's why the logo pops in late, and why a 932 KB hero gets queued behind everything else.

The fix is to make it a prop instead of a constant, and let callers opt in:

// ImageSlot.tsx — add to the props interface
interface ImageSlotProps {
  /** Above-the-fold artwork: load immediately instead of deferring. */
  priority?: boolean;
  // …existing props
}

// and in the <img>
<img
  src={src}
  alt={label}
  loading={priority ? 'eager' : 'lazy'}
  decoding={priority ? 'sync' : 'async'}
  fetchPriority={priority ? 'high' : 'auto'}
  className={...}
/>

Then pass priority on the handful of images that are visible before any scrolling — the nav logo, the home hero, and each page's banner. Leave everything else lazy.

Don't just blanket-lazy everything

A common mistake is adding loading="lazy" to all 101 tags. On above-the-fold images that hurts: it delays the largest visible element and pushes back your LCP score. Only below-the-fold images should be lazy.

3Give the hero a head start

Two attributes plus one line of HTML tell the browser what to fetch first. Free, no dependency, and it's the difference between "hero appears" and "hero fades in".

The heavy one is cocycle-hero.png — the 1440×684 background behind the /cococycle-hub hero, at 932 KB today and 29 KB once converted. That's your largest above-the-fold image, so it's the one worth prioritising. 

<!-- preload the hero background, before React even boots -->
<link rel="preload" as="image"
      href="/assets/cocycle-hero.webp"
      type="image/webp" fetchpriority="high" />

<!-- and on the nav logo: fetch it in the first round trip -->
<img src={logo} alt="Coconoto" fetchPriority="high" decoding="sync" />

Note that the three home-hero-* slots are still empty strings in src/pages/figma/images.ts, so there's nothing to preload on the home page yet. When you do supply that artwork, give it the same treatment.

Also add decoding="async" to the below-fold images. It moves image decoding off the main thread so scrolling stays smooth instead of stuttering.

4Turn on long-lived caching for hashed assets

Vite fingerprints every asset filename with a content hash (cocycle-hero-a3f9c2.webp), which means the content at a given URL never changes — so it can be cached forever. Vercel does not set that header automatically for a Vite app (it only does for Next.js). It falls back to max-age=0, must-revalidate, so returning visitors re-download images they already have.

Add a headers block to vercel.json — it sits alongside your existing rewrites:

{
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [
        { "key": "Cache-Control",
          "value": "public, max-age=31536000, immutable" }
      ]
    }
  ],
  "rewrites": [ /* …your existing rules, unchanged… */ ]
}
This is safe because of the hash

immutable is only correct for fingerprinted filenames — which is exactly what Vite produces. Never apply it to index.html, or users will be stuck on a stale build. The rule above is scoped to /assets/ only, so it's fine.

5Serve the right size to each screen

Once you have WebP versions, you can offer the browser a choice and let it pick. This is what saves the most on phones, where a 1200px image is a waste on a 390px screen. 

<img
  src="hero-1200.webp"
  srcSet="hero-640.webp 640w,
          hero-1200.webp 1200w,
          hero-1920.webp 1920w"
  sizes="(max-width: 640px) 100vw, 1200px"
  alt="…"
/>

You don't need a CDN or a paid service for this — sharp (already installed as a dev dependency) can emit all three widths in the same script. It's only worth doing for the handful of large hero and background images; leave the small ones alone.

6Make the build do this automatically, forever

Once the existing images are fixed, the next 7 MB photo someone drops into src/assets reintroduces the problem. Two free ways to prevent that:

  • Re-run the script whenever new images are added — node scripts/optimize-images.mjs --write. Simplest, no new dependencies.
  • Automate it in the build — add vite-plugin-image-optimizer (free, MIT, uses the sharp you already have) to vite.config.ts so every npm run build compresses images on the way out. Costs build time, saves you remembering.

There's also AVIF, which beats WebP by another 20–30%. It's free to generate but slower to encode and has patchier support, so treat it as a later optimisation rather than a first move. WebP is where the 85% is.

7Delete what you don't use

dist/ has accumulated stale build generations because emptyOutDir: false is set in vite.config.ts. That's harmless for visitors — the live index.html only points at the newest hashed files — but it does mean your repo and any full-directory upload carry dead weight. Separately, it's worth checking whether all 103 source images are actually referenced anywhere. Unused images that are never imported don't ship, but they do bloat the repo and confuse the next person.

8What not to bother with

Vercel's built-in Image Optimization is not the free win it looks like

The Hobby plan does include 5,000 image transformations/month — but its Fair Usage Policy restricts Hobby to non-commercial personal use only. Coconoto is a commercial business, so leaning on it is against the terms and could get the project flagged. It's also built around Next.js's <Image> component, which you aren't using. Skip it.

Free-tier image CDNs (Cloudinary, ImageKit) solve a problem you don't have

They're genuinely free to start, but they add a third-party dependency, an upload step, and a new way for images to break — in exchange for optimisation you can get locally from sharp in about ten seconds. Reach for one only if you later need on-the-fly transforms driven by user uploads.

9Do it in this order

  1. Run the report: node scripts/optimize-images.mjs — confirm the numbers yourself.
  2. Apply: --write, then npm run build, then check DevTools → Network.

  4. Add decoding="async" to below-fold images, fetchpriority="high" to the hero.
  5. Add the headers block to vercel.json and redeploy.
